# Phase 0-1: 要件定義とスコープ

## この章のゴール

DeciTima というプロダクトが「何を解くのか」「何を解かないのか」を言語化する。
ここが曖昧なままスキーマやアーキテクチャの設計に進むと、抽象的で使いどころのない
モデルができあがる。逆に、対象を絞りすぎると Phase 6 以降の拡張で作り直しになる。

この章では次を確定させる。

- DeciTima が扱う「問題クラス」の範囲
- スコープ外(非ゴール)の明示
- 責務分離の原則 ── なぜ LLM に計算させないのか
- MVP(Phase 0〜5)で作るものの一覧
- 設計を検証するための 2 つの題材 ── Route Planner と Shift Scheduler

---

## 1. DeciTima が解く問題は何か

### 1.1 ひとことで言うと

> **人間が自然言語で表現した「条件つきの決めごと」を構造化し、決定論的なアルゴリズムで解いて、意思決定を支援する。**

「条件つきの決めごと」とは、次のような形をしている。

```
・やりたいこと      … 目的(何を最大化 / 最小化したいか)
・守るべき条件      … 制約(絶対に破れない条件 / できれば満たしたい条件)
・選べる範囲        … 変数・選択肢(どこを動かせるのか)
```

例:

| 場面 | 目的 | 制約 | 選べる範囲 |
| --- | --- | --- | --- |
| 旅行の計画 | 移動時間を最小化 | 予算 5 万円以内 / 2 日間 / 浅草は必ず訪問 | 訪問先の順番と組み合わせ |
| 勤務シフト | 人件費を最小化 | 各時間帯に必要人数 / 週 40 時間まで / 希望休 | 誰をいつ入れるか |
| 配送ルート | 総走行距離を最小化 | 積載量 / 時間指定 | 配送順・車両割当 |

これらはいずれも「**組合せの中から、条件を満たす最良のものを選ぶ**」という同じ構造を
持っている。DeciTima はこの構造 ── **最適化問題(optimization problem)** ── を
共通の土台として扱う。

### 1.2 対象とする問題クラス

MVP では次の 3 カテゴリを扱う。いずれも README のユースケースに対応している。

| カテゴリ | 中身 | 代表アルゴリズム | 対応ユースケース |
| --- | --- | --- | --- |
| **探索 (Search)** | 状態空間から目標を見つける | 二分探索 / BFS / DFS | 各種の基礎 |
| **グラフ (Graph)** | ノードとエッジで表せる問題 | Dijkstra / A* / トポロジカルソート | Route Planner / Project Manager |
| **組合せ最適化 (Combinatorial Optimization)** | 割当・選択・順序づけ | 貪欲法 / 動的計画法 / バックトラッキング / 分枝限定法 | Shift Scheduler / Travel Planner / Logistics |

Phase 0 の設計は、この 3 カテゴリすべてを 1 つの共通スキーマとエンジン
インターフェースで受け止められることを目標にする。ただし検証は MVP に含まれる
Route Planner(グラフ)と Shift Scheduler(組合せ最適化)の 2 つで行う。

## 2. 非ゴール ── DeciTima が「やらない」こと

設計を締めるうえで、やらないことの明示はやることの明示と同じくらい重要になる。

### 2.1 LLM に最適解を計算させない

DeciTima の設計上の一丁目一番地。**LLM は計算エンジンではない。**

LLM に任せるのは次の 3 つだけ(いずれも Phase 10 以降)。

1. 自然言語 → 構造化された問題定義(Structured Problem)への変換
2. 問題の性質からアルゴリズム候補を提示する補助
3. アルゴリズムが出した結果を人間向けに説明する

経路探索・動的計画法・スケジューリング・制約判定・数値最適化・ベンチマークは、
**すべて決定論的なアルゴリズムが担当する。**

理由:

| 求めるもの | LLM 単独では | 決定論的アルゴリズムなら |
| --- | --- | --- |
| 再現性 | 同じ入力でも出力が揺れる | 同じ入力 → 必ず同じ出力 |
| 制約遵守 | 「だいたい満たす」に留まる | 検証で 100% 保証できる |
| 最適性 | 最良である保証がない | アルゴリズムによっては最適を保証 |
| 監査 | なぜその答えかを追跡しにくい | 実行過程を記録・再現できる |

### 2.2 汎用ソルバーの新規開発ではない

DeciTima は OR-Tools や Gurobi のような「あらゆる最適化問題を解く汎用ソルバー」を
ゼロから作るプロジェクトではない。作るのは次の 2 つ。

- **学習目的の手実装**: BFS / Dijkstra / バックトラッキング等を自分で書き、
  再現性・計算量・設計判断を説明できる状態にする。
- **実務目的の産業ソルバー連携**: 手実装がスケールしない規模では、同じ
  インターフェースの裏で OR-Tools / networkx / scipy を呼ぶ。

この「2 トラック」方針の詳細は Phase 0-4 で扱う。

### 2.3 一般的な AI チャットアプリではない

`decitima-api` はテンプレート由来の LLM チャット機能を持っているが、DeciTima は
チャットでの雑談や自由回答を目的としない。ユーザーとの対話は
「AI が理解した問題定義を確認してもらう」ための Human-in-the-loop に限定する
(README 11 節)。

## 3. 責務分離の原則

DeciTima のパイプラインは 7 つのステージに分かれる。各ステージは
「入力」「やること」「出力」がはっきり決まっており、独立してテストできる。

```
┌────────────┐
│ 1. User    │  自然言語で要求を入力(MVP では構造化 JSON を直接入力)
└─────┬──────┘
      ▼
┌────────────┐
│ 2. LLM     │  意図理解・条件抽出・問題構造化           ← Phase 10〜
└─────┬──────┘
      ▼
┌────────────────────┐
│ 3. Structured      │  OptimizationProblem(共通スキーマ)
│    Problem         │  ここが LLM と Algorithm の "共通言語"
└─────┬──────────────┘
      ▼
┌────────────────────┐
│ 4. Validation      │  「問題定義として妥当か?」                ← Phase 2
│                    │  budget >= 0 / required_staff <= available 等
└─────┬──────────────┘
      ▼
┌────────────────────┐
│ 5. Algorithm       │  決定論的な計算。候補解を生成            ← Phase 1〜
│    Engine          │  手実装トラック / 産業ソルバートラック
└─────┬──────────────┘
      ▼
┌────────────────────┐
│ 6. Verification    │  「計算結果が制約を満たすか?」            ← Phase 2
│                    │  1 つでも hard 制約違反 → 解は INVALID
└─────┬──────────────┘
      ▼
┌────────────────────┐
│ 7. Simulation /    │  条件を変えて複数シナリオを比較          ← Phase 9
│    Comparison      │  「どの条件ならどの選択をすべきか」
└─────┬──────────────┘
      ▼
┌────────────┐
│ LLM        │  結果を人間向けに説明                       ← Phase 12〜
└─────┬──────┘
      ▼
   意思決定
```

### なぜここまで分けるのか

ステージを混ぜると、次のような問いに答えられなくなる。

- 「解が間違っている」── アルゴリズムのバグか? 問題定義が間違っていたのか?
- 「制約を満たしていない」── アルゴリズムが破ったのか? そもそも実行不可能な問題だったのか?
- 「昨日と違う答えが出た」── 入力が変わったのか? アルゴリズムが非決定的なのか?

**Validation(4)と Verification(6)を分けている**のがこの設計の肝になる。

- Validation = 「問題として意味をなすか」。`budget >= 0`、`duration > 0`。
- Verification = 「出てきた解が条件を守っているか」。`work_hours <= max_hours`、`requested_holiday == OFF`。

前者は Algorithm Engine に渡す**前**、後者は候補解が出た**後**。
役割も、失敗したときの意味も、全く違う。詳細は Phase 0-6。

## 4. MVP スコープ(Phase 0〜5)

README 20 節のとおり、MVP は Phase 0 から Phase 5 まで。

| Phase | 目的 | この Phase で増えるもの |
| --- | --- | --- |
| **0** | 責務分離と共通モデルの確立 | 設計文書(この textbook)+ 低リスクな骨組み |
| **1** | 決定論的な計算基盤 | 手実装の Binary Search / BFS / DFS / Dijkstra、`AlgorithmStrategy`、実行 API、Unit Test |
| **2** | 入力と制約の検証 | Pydantic Validation / Constraint Checker / Solution Verification |
| **3** | アルゴリズムの定量評価 | 実行時間・操作回数・メモリ計測、比較 UI、可視化 |
| **4** | グラフアルゴリズムの実問題適用 | Route Planner(Graph Model / Dijkstra / A* / 経路可視化) |
| **5** | 制約最適化の実装 | Shift Scheduler(Staff/Shift モデル / 制約定義 / 貪欲法・バックトラッキング・分枝限定法 / シフト可視化) |

### MVP における「問題定義」の入り口

LLM は Phase 10 から。したがって **Phase 0〜9 では、ユーザー(または API 呼び出し側)が
構造化済みの `OptimizationProblem` を直接投入する。** 自然言語は受け取らない。

これは制約ではなく、むしろ設計を素直にする。共通スキーマが「LLM の出力先」ではなく
「API の入力そのもの」になるので、スキーマの良し悪しがすぐにコードへ跳ね返る。

### MVP 完成時点で経験できること

Next.js / Tamagui / FastAPI / PostgreSQL / REST API / Algorithm Engine / Validation /
Verification / BFS・Dijkstra 等 / Benchmark / 可視化 / Route Planner / Shift Scheduler。

## 5. 設計を検証する 2 つの題材

Phase 0 の設計(スキーマ・エンジン・検証)は、抽象論で終わらせず
**必ずこの 2 つの具体問題で「本当に表現できるか」を確認する。**

### 5.1 Route Planner(Phase 4 の題材)

地図をグラフとみなし、出発地から目的地までの最短経路を求める。

| 要素 | 内容 |
| --- | --- |
| 目的 | 総移動距離(または所要時間)の**最小化**。単一目的。 |
| 制約 | 通行禁止のエッジ / 特定ノードの必須経由 / 最大移動時間 |
| 変数 | どのエッジをたどるか(経路そのもの) |
| データ | ノード集合、エッジ集合(重み付き)、start、goal |
| アルゴリズム | Dijkstra、A*(将来 BFS も比較用に) |
| 検証項目 | 経路が連結している / start と goal を結んでいる / 禁止エッジを使っていない / 必須ノードを通っている |

### 5.2 Shift Scheduler(Phase 5 の題材)

スタッフを勤務スロットに割り当てる。

| 要素 | 内容 |
| --- | --- |
| 目的 | 人件費の**最小化** + 希望休の充足率**最大化**。**多目的**(重み付き)。 |
| 制約(hard) | 各スロットの必要人数 / 週の勤務時間上限 / 最大連続勤務日数 / スタッフごとの勤務可能時間 |
| 制約(soft) | 希望休(できれば OFF に)/ 勤務時間の均等化 |
| 変数 | 「スタッフ s をスロット t に入れるか」の割当 |
| データ | スタッフ一覧(時給・スキル・勤務可能時間)、スロット一覧(必要人数・必要スキル)、希望休 |
| アルゴリズム | 貪欲法、バックトラッキング、分枝限定法(将来 OR-Tools CP-SAT を実務トラックで) |
| 検証項目 | 全スロットで必要人数を満たす / 勤務時間が上限以下 / 希望休がどれだけ守られたか(soft なので違反数を数える) |

### 5.3 なぜこの 2 つなのか ── 性質が対照的だから

| 観点 | Route Planner | Shift Scheduler |
| --- | --- | --- |
| 問題の型 | グラフ探索 | 組合せ最適化(割当) |
| 目的 | 単一目的 | 多目的(重み付き) |
| 制約の性質 | ほぼ hard のみ | hard と soft の混在 |
| 解の形 | ノードの列(経路) | 二次元の割当表 |
| 最適解の求めやすさ | 多項式時間で最適が出る | 一般に NP 困難、規模で手実装が破綻する |

**この 2 つを 1 つのスキーマ・1 つのエンジンインターフェースで扱えれば、
設計は十分に汎用的**と判断できる。逆に、どちらか一方でも無理な表現を
強いられるなら、スキーマを見直す。

## 6. 機能要件(FR)

MVP で API が満たすべき機能。

| ID | 要件 |
| --- | --- |
| FR-1 | 構造化された `OptimizationProblem` を受け取り、`CandidateSolution` を返す |
| FR-2 | 指定された、または問題タイプに対応する複数のアルゴリズムで解ける |
| FR-3 | すべての解に対して制約充足の検証結果(`violations`)を付与する |
| FR-4 | 同じ問題を複数アルゴリズムで解いた結果を比較できる(Phase 3) |
| FR-5 | アルゴリズムの実行時間・操作回数などのメトリクスを記録する(Phase 3) |
| FR-6 | 問題・解・検証結果を永続化し、後から参照できる |
| FR-7 | 認証済みユーザーのみが solve を実行でき、レート制限がかかる |

## 7. 非機能要件(NFR)

DeciTima の存在意義そのもの。

| ID | 要件 | どう担保するか |
| --- | --- | --- |
| NFR-1 **再現性** | 同じ入力から必ず同じ出力 | アルゴリズムを決定論的に実装。乱数を使う場合は seed を入力に含める |
| NFR-2 **検証可能性** | すべての解に「制約を満たすか」の判定が付く | Verification ステージを必須にする。検証なしの解は返さない |
| NFR-3 **比較可能性** | アルゴリズム間・手実装 vs ソルバー間を同じ土俵で比べられる | 全アルゴリズムが同一の `AlgorithmStrategy` インターフェース・同一スキーマ |
| NFR-4 **説明可能性** | なぜその解になったかを説明できる | 解に `produced_by`(使用アルゴリズム)と `metrics` を必ず付ける。文章生成は Phase 12 |
| NFR-5 **パフォーマンス** | 実用的な規模を実用的な時間で解く | Phase 3 で定量化。手実装の限界を測り、超えたら産業ソルバートラックへ |

## 9. まとめ

- DeciTima は「条件つきの決めごと」= 最適化問題を共通の土台として扱う。
- LLM は理解・構造化・説明のみ。計算・検証・最適化は決定論的アルゴリズム。
- パイプラインは 7 ステージ。とくに Validation(問題の妥当性)と
  Verification(解の制約充足)を分離する。
- MVP は Phase 0〜5。LLM は含まず、構造化 JSON を直接入力する。
- 設計は Route Planner と Shift Scheduler の 2 題材で必ず検証する。
  この 2 つは性質が対照的なので、両方を扱えれば汎用性は十分。

次章(Phase 0-2)では、この要件を満たす**共通スキーマ**
`OptimizationProblem` / `Constraint` / `Objective` / `CandidateSolution` を設計する。
