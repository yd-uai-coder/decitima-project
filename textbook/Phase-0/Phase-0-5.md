# Phase 0-5: 計算量とパフォーマンス設計

## この章のゴール

7 項目チェックリストの「5. Complexity」にあたる。

- MVP で使うアルゴリズムの時間・空間計算量を整理する
- 想定する入力サイズと、手実装が破綻する境界を見積もる
- Phase 3 のベンチマークで測る指標を確定する
- 長時間計算への対処方針(同期実行 + タイムアウト)を決める

計算量の議論は「なんとなく速そう」を排除し、**アルゴリズム選択(Phase 0-4 の
rule-based)の根拠**を与える。

---

## 1. なぜ Phase 0 で計算量を整理するのか

- **アルゴリズム選択の根拠になる**。「A* は Dijkstra と同じ最悪計算量だが、
  良いヒューリスティックがあれば探索ノードが激減する」── こういう判断を
  rule-based セレクタに落とすには理論値が要る。
- **手実装トラックの限界を先に知る**。バックトラッキングは最悪 O(kⁿ)。
  「スタッフ 20 人 × 7 日ならもう手実装では終わらない」を Phase 5 で
  慌てて気づくのではなく、いま見積もる → 産業ソルバートラック(Phase 0-4)の
  導入時期を計画に織り込める。
- **ベンチマークの設計図になる**。Phase 3 で「何を」「どの入力サイズで」測るかを
  ここで決めておく。

---

## 2. MVP アルゴリズムの計算量

記号: V = ノード数, E = エッジ数, n = 要素数(スタッフ×スロット等), k = 分岐数, W = 容量

### 2.1 探索 (Phase 1)

| アルゴリズム | 時間 | 空間 | 備考 |
| --- | --- | --- | --- |
| Binary Search | O(log n) | O(1) | ソート済み前提 |
| BFS | O(V + E) | O(V) | 無重みグラフの最短経路 |
| DFS | O(V + E) | O(V)(再帰スタック) | 経路探索・連結判定 |

### 2.2 グラフ (Phase 4 / Route Planner)

| アルゴリズム | 時間 | 空間 | 備考 |
| --- | --- | --- | --- |
| Dijkstra(二分ヒープ) | O((V + E) log V) | O(V) | 非負重み。手実装は `heapq` |
| A* | 最悪 O((V + E) log V)、実際はヒューリスティック次第で激減 | O(V) | 許容的ヒューリスティックが必要。座標があればユークリッド距離 |
| networkx `shortest_path` | 実装依存(内部は Dijkstra 相当) | ─ | 実務トラック。C 実装で定数倍が速い |

### 2.3 組合せ最適化 (Phase 5 / Shift Scheduler ほか)

| アルゴリズム | 時間 | 空間 | 最適性 |
| --- | --- | --- | --- |
| 貪欲法(Greedy) | O(n log n) 程度 | O(n) | 保証なし。hard 制約を破ることもある |
| 動的計画法(0/1 ナップサック) | O(nW) | O(nW) → O(W) に削減可 | 最適 |
| バックトラッキング | 最悪 O(kⁿ)、枝刈りで大幅減 | O(n)(深さ) | 探索しきれば最適 |
| 分枝限定法(B&B) | 最悪 O(kⁿ)、下界で枝刈り | O(n)〜O(kⁿ) | 最適(打ち切らなければ) |
| OR-Tools CP-SAT | 実用上は多くの規模で現実的、理論的には NP 困難 | ─ | 最適 or 実行不能を判定 |

## 3. 想定入力サイズと手実装の破綻点

### 3.1 Route Planner

| シナリオ | V | E | 手実装 Dijkstra | 判断 |
| --- | --- | --- | --- | --- |
| デモ用の小地図 | 〜50 | 〜150 | 一瞬 | 手実装で十分 |
| 市街地レベル | 〜5,000 | 〜15,000 | 数十 ms | 手実装で十分 |
| 都市全域(OSM 相当) | 〜10⁶ | 〜10⁶ | 数百 ms〜数秒。定数倍で networkx / 専用ライブラリが有利 | 実務トラック検討 |

Dijkstra は多項式時間なので「破綻」はしにくい。差が出るのは**定数倍**
(Python の手実装 vs C 実装)。Phase 3 でこの差を実測する。

### 3.2 Shift Scheduler ── ここが本番

割当の探索空間はおおよそ「各スロットに入れうるスタッフの組合せ」の積。
バックトラッキングは枝刈りで劇的に減るが、それでも:

| シナリオ | スタッフ | 日数 | スロット/日 | バックトラッキング | 判断 |
| --- | --- | --- | --- | --- | --- |
| 教材の小例 | 3 | 2 | 2 | 一瞬 | 手実装で十分 |
| 小規模店舗 | 8 | 7 | 3 | 枝刈り次第。秒〜十数秒 | 手実装の上限に近い |
| 中規模(README の例) | 20 | 7 | 3 | 現実的な時間で終わらない可能性大 | **産業ソルバー(CP-SAT)必須** |

**結論**: Shift Scheduler は Phase 5 で手実装(貪欲・バックトラッキング)を
「小規模で最適解を出し、原理を学ぶ」用途に位置づけ、**中規模以上は
OR-Tools CP-SAT トラック**を用意する。この判断を Phase 0 時点で計画に入れておく。

## 4. Phase 3 ベンチマークで測る指標

README 14 節・Phase 3 の deliverable に沿って、測定項目を確定する。

| 指標 | 測り方 | 何がわかるか |
| --- | --- | --- |
| **実行時間** | `time.perf_counter()` で `solve()` を挟む。複数回の中央値 | 実用性。手実装 vs ソルバーの定数倍 |
| **操作回数** | アルゴリズム内でカウンタをインクリメント(比較回数・ノード展開数) | 理論計算量の裏付け。実装の良し悪し |
| **メモリ使用量** | `tracemalloc` のピーク | 空間計算量の裏付け。大規模入力の可否 |
| **入力サイズ別** | V / n を変えて上記を再測定し、曲線を描く | どの規模でどのアルゴリズムに切り替えるべきか |
| **解の品質** | 目的関数値。最適解(または B&B の最良)との比 | 貪欲法など近似アルゴリズムの精度 |
| **制約違反数** | `CandidateSolution.violations` の hard/soft 件数 | 近似アルゴリズムがどれだけ「ズル」をしたか |

### 測定を仕込む場所

- **操作回数**は `solve()` の中でカウントする必要がある。`AlgorithmStrategy` に
  「計測モード」を持たせるか、`solve()` が返す `CandidateSolution.metrics` に
  `_ops` を入れる規約にする。Phase 3 で確定。Phase 0 では「metrics 辞書に
  アルゴリズム内部の計測値を入れてよい」とだけ決めておく。
- **実行時間・メモリ**は `solve()` の外(ベンチマークサービス)で測る。

## 5. 長時間計算への対処

### 5.1 MVP は「同期実行 + タイムアウト」

- `POST /solve` は同期。計算が終わるまでレスポンスを返さない。
- `SolveService` が `solve()` にタイムアウト(既定 10 秒程度、設定で変更可)を課す。
  超えたら `SolveTimeoutError`(`AppError` 派生 → 504 相当)。
- タイムアウトした場合でも、B&B のように「その時点の最良解」を持つアルゴリズムは
  `status` を `valid`/`invalid` にしたうえで「打ち切り」フラグを metrics に立てて返す
  選択肢を Phase 5 で検討。

### 5.2 なぜ最初からジョブキューにしないのか(YAGNI)

- Celery / arq などの非同期ジョブ基盤はインフラを増やす(ワーカー、結果ストア、
  ポーリング or WebSocket)。
- MVP の題材(小〜中規模の Route / Shift)は同期 + タイムアウトで十分間に合う。
- 本当に必要になるのは Phase 8(Logistics、複合最適化)あたり。そのとき
  `infrastructure/` にジョブ基盤を足す。Phase 0 の設計は「同期前提だが、
  `SolveService` を将来ジョブ化しても API 契約(問題 ID で結果を引く)は
  変わらないように」する ── つまり **solve の結果は必ず永続化し、`solution_id` で
  後から取得できる**エンドポイントも用意しておく(Phase 0-7)。

### 5.3 Route Planner の必須経由制約と計算量

Phase 0-2 の Route の例で「C を必ず経由」という `RequiredInclusionConstraint` があった。
必須経由ノードが m 個あると、厳密には「m! 通りの訪問順 × 各区間の最短経路」= 
小さな巡回セールスマン問題になる。MVP では:

- 必須経由が 0〜1 個: そのまま「start→経由→goal」を分割して Dijkstra を 2 回。
- 必須経由が 2 個以上: Phase 4 で「m が小さければ順列全探索、大きければ近似」を
  設計する。Phase 0 では「制約としてスキーマに載る」ことだけ確認済み。

---

## 6. まとめ

- グラフアルゴリズム(Dijkstra / A*)は多項式時間。差は定数倍で、Phase 3 で実測する。
- 組合せ最適化のバックトラッキング/B&B は最悪指数時間。**Shift Scheduler は
  中規模で手実装が破綻する**ため、Phase 5 で OR-Tools CP-SAT トラックを用意する
  ── この判断を Phase 0 で計画に織り込む。
- Phase 3 で測るのは 実行時間 / 操作回数 / メモリ / 入力サイズ別 / 解の品質 / 制約違反数。
  操作回数は `solve()` 内でカウントし metrics に入れる規約。
- MVP は同期実行 + タイムアウト。ジョブキューは Phase 8 まで導入しない(YAGNI)。
  ただし solve 結果は必ず永続化し、`solution_id` で後から引ける設計にしておく。

次章(Phase 0-6)では、計算の前後に置く 2 つの検証 ──
Validation(問題定義の妥当性)と Verification(解の制約充足)── を設計する。
